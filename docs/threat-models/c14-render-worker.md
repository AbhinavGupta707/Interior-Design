# C14 render-worker threat model

## Protected assets and trust boundaries

C14 protects tenant/project isolation, exact C10/C13 provenance, active rights decisions, canonical-to-derived authority separation, render requests and idempotency effects, private lease fences, disk capacity, local workspaces, renderer executable/script identity, artifact bytes/hashes, internal object keys, opaque access grants, immutable result history, and privacy-minimised telemetry.

The main trust boundaries are:

- authenticated caller to strict, project-authorised API routes;
- API service to authoritative C10/C13/profile ports;
- application transactions to forced-RLS PostgreSQL tables;
- renderer worker to the constrained cross-tenant claim function;
- worker to the private lease/heartbeat/publication control plane;
- worker to source-object reads and a credential-free renderer subprocess;
- renderer outputs to mandatory GLB/PNG/OpenEXR validation;
- control plane to content-addressed derived-object storage; and
- authorised caller to an opaque, exact artifact access gateway.

C4/C5 remain canonical dimensional truth. C10/C14 geometry and media are derived proposals/visualisations. A still, EXR pass, segmentation image, GLB, or illustrative enhancement cannot establish exact dimensions, structure, regulation, cost, availability, procurement, or professional approval.

## Database and principal assumptions

The migration/function owner is not a runtime credential. Since the tenant queue tables use `FORCE RLS` while the constrained claim intentionally discovers eligible work across tenants, that protected non-login owner must be able to bypass RLS; API and worker principals must never inherit or assume it. Production API and worker roles must be distinct non-owner, `NOSUPERUSER`, `NOCREATEDB`, `NOCREATEROLE`, `NOINHERIT`, `NOBYPASSRLS` principals. API transactions set a validated `app.tenant_id` locally. The claim function is the only intended cross-tenant discovery hook and must retain its constrained parameters, fixed search path, `PUBLIC` revocation, volume lock, capability filter, and `SKIP LOCKED` behavior.

The private worker control-plane adapter may perform fenced heartbeat/failure/publication operations, but it must not expose lease tokens or cross-tenant lookup endpoints publicly. Renderer subprocesses receive neither database nor object-store credentials; the parent performs exact reads/uploads after validation.

The opaque artifact gateway is a separate trusted component. It must validate the complete signed claim, enforce expiry and single exact object response semantics, set the bound media type/length, avoid redirects that disclose a key, and emit an access audit signal without logging the token or URL.

## Operational detection and response

Alert on repeated claim validation failures, lease fencing conflicts, stale cancellations, disk-admission loss, executable/script hash mismatch, process timeout/output overflow, corrupt GLB/EXR/PNG results, source revalidation withdrawal, content-address collision metadata mismatch, publication-fence loss, and unusual artifact-access issuance volume. Metrics must use bounded labels only: profile/capability class, stage, outcome, and safe code.

On renderer identity mismatch, disable the affected capability and quarantine the host; do not auto-update the pin. On corrupt output, retain only non-sensitive safe-code/audit facts and quarantine inaccessible object bytes by hash for investigation. On suspected access-gateway key compromise, rotate gateway signing material and invalidate outstanding grants; immutable artifact hashes/results need not be rewritten. On low disk, stop claiming, allow current fenced work to fail/release, and investigate orphan retention without deleting referenced objects.

## Residual risks and non-claims

- Root composition still must prove correct C10/C13/L1 adapters, runtime role grants, object-gateway enforcement, route registration, and configuration separation.
- The authorised Blender host and production GLB/OpenEXR inspectors have not been exercised in this lane. Static driver code plus inert fake-process tests are not real render, pass, GPU, Metal, CUDA, OptiX, or Cycles evidence.
- Content-addressed orphan collection is an operational follow-up; incorrect reference discovery could delete shared bytes, so conservative age/reference checks are mandatory.
- A compromised migration/function owner can bypass controls; database administration, image provenance, host hardening, patching, sandboxing, and supply-chain attestation remain deployment responsibilities.
- Bounded parsing and offline flags reduce exposure but do not prove Blender or third-party native libraries are vulnerability-free. Run the renderer on an isolated authorised host with OS resource/network controls.
- Rendered appearance and optional enhancement may be misleading. They remain labelled derived/illustrative and cannot become canonical dimensional, structural, regulatory, cost, availability, procurement, or professional truth.
